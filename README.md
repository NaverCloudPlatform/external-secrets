# External Secrets Operator for NAVER Cloud Platform

This repository is a fork of [External Secrets Operator](https://external-secrets.io/)
(ESO) that adds the `ncloud` provider for
[NAVER Cloud Platform Secret Manager](https://www.ncloud.com/product/security/secretManager).
It is upstream ESO plus that provider and the build changes listed under
[Changes from upstream](#changes-from-upstream).

> **Community fork.** This repository is maintained by the NAVER Cloud NKS
> team and is not part of the upstream external-secrets project. Issues and
> pull requests about the `ncloud` provider and this fork's build are handled
> here. Problems in other providers, or in code shared with upstream, belong
> in the [upstream repository](https://github.com/external-secrets/external-secrets/issues).

## What the `ncloud` provider does

- **Read** secrets from Secret Manager into Kubernetes Secrets
  (`ExternalSecret`, `ClusterExternalSecret`): a single secret by name or by
  64-character lowercase hexadecimal secret ID, one key of a JSON value with
  `property`, every key
  with `dataFrom.extract`, and many secrets with `dataFrom.find` (name prefix
  and regular expression).
- **Write** Kubernetes Secrets to Secret Manager (`PushSecret`,
  `ClusterPushSecret`): create a secret when it is missing, update a whole
  JSON value or one key of it, and delete what the operator created. A
  secret whose memo lacks the `managed-by: external-secrets` line is never
  modified.
- **Deletion lifecycle** that follows Secret Manager: a delete requests
  deletion, and the secret stays recoverable for the 7-day grace period,
  unless the store sets `forceDeleteWithoutRecovery: true`.
- **Metadata** reads with `metadataPolicy: Fetch` (status, planned destroy
  time, and the other fields of Get Secret Detail).
- **Stages** (`previous`, `active`, `pending`) through `remoteRef.version`;
  omitted means `active`.

## Compatibility

| Component | Version |
|---|---|
| Upstream External Secrets Operator | v2.14.0 |
| Kubernetes | verified on 1.36.2 (Ncloud Kubernetes Service) |
| Secret Manager regions | KR (`https://ocapi-kr.ncloud.com/secretmanager` for secrets protected by an isolated KMS key, `https://secretmanager.apigw.ntruss.com` for existing secrets protected by a global key), JPN (`https://ocapi-jp.ncloud.com/secretmanager`) |

Secret Manager is offered in the KR and JPN regions of the public NAVER
Cloud Platform. Clusters in other regions reach those endpoints over the
public internet.

## Installation

### NKS add-on (recommended on Ncloud Kubernetes Service)

Install the `external-secrets` add-on from the cluster's add-on catalog on
Kubernetes 1.36 or later. The add-on installs the operator into the
`external-secrets` namespace with the CRDs, the validating webhook and the
certificate controller. See the
[add-on guide](https://guide.ncloud-docs.com/docs/k8s-k8suse-addon-external-secrets)
(Korean).

### Helm chart

Each release attaches the packaged chart, `external-secrets-<version>.tgz`.
It is the upstream chart with the `ncloud` fields in its CRDs, carries all
the CRDs, and pins the image the release was built from, so it installs as
it is:

```bash
helm install external-secrets \
  https://github.com/NaverCloudPlatform/external-secrets/releases/download/v2.14.0/external-secrets-2.14.0.tgz \
  --namespace external-secrets --create-namespace
```

Keep the release name and the namespace `external-secrets`. The controller's
ServiceAccount, `external-secrets/external-secrets`, is what a Pod Identity
association names, and the NKS add-on runs under the same names, so the
association still applies after a move to the add-on. The chart pulls from
the KR registry; in another region, add the registry the release notes list
for that region:

```bash
  --set image.repository=<registry>/nks/external-secrets \
  --set webhook.image.repository=<registry>/nks/external-secrets \
  --set certController.image.repository=<registry>/nks/external-secrets
```

Do not install `deploy/charts/external-secrets` from a checkout. Its CRD
templates are generated by `make helm.generate` and are not committed, and
the `bitwarden-sdk-server` subchart is fetched only at packaging, so such an
install fails on the missing subchart and, after `helm dependency build`,
installs no CRDs. Build the release asset with
`make helm.package.release` instead (see
[Building from source](#building-from-source)).

`helm uninstall` removes the operator and keeps the CRDs, and with them
every store, every `ExternalSecret` and the Kubernetes Secrets those own.
The chart marks its CRDs `helm.sh/resource-policy: keep` for that;
upstream's chart does not, and uninstalling it deletes all of them. Helm
reads the mark from the manifest it stored for the release, not from the
chart, so a release without it loses its CRDs: one that set the annotation
to `null`, or one upgraded with `--reuse-values` from a chart that did not
have the default. Check before uninstalling:

```bash
helm get manifest external-secrets --namespace external-secrets \
  | grep -c 'helm.sh/resource-policy: keep'
```

The count is one per CRD, 25 by default. If it is 0, upgrade the release
first, with the chart version it already runs and
`--reuse-values --set 'crds.annotations.helm\.sh/resource-policy=keep'`.
Without `--reuse-values`, a `--set` drops the values the release was given
before. With it, Helm also keeps the defaults the release runs with, so a
newer chart given here would not bring its image tag.

To remove the CRDs as well, delete them with `kubectl` before uninstalling,
while the controller is still running. The controller puts finalizers on
what it manages, every `ExternalSecret` among them, and only it removes
them. After the uninstall a resource that carries one cannot be deleted,
so a CRD stays in `Terminating`, and so does a namespace that holds such a
resource, until a controller runs again. Deleting the CRDs deletes every
resource created from them: an `ExternalSecret` takes the Kubernetes
Secret it owns with it, and a `PushSecret` with `deletionPolicy: Delete`
deletes the secrets it pushed from the provider.

The NKS add-on does not install over this chart: while a release under the
names above is installed, the add-on's install is refused. To move to the
add-on, uninstall this release, which keeps the CRDs, and then install the
add-on. Its controller picks up the stores and `ExternalSecret`s that were
left. The
[add-on guide](https://guide.ncloud-docs.com/docs/k8s-k8suse-addon-external-secrets)
(Korean) describes a move that does not use `helm uninstall`, for an
installation that would not keep its CRDs.

Upstream images and the upstream chart do not include this provider. A
cluster that runs this image with upstream CRDs, or upstream images with
these CRDs, rejects `ncloud` stores at admission.

## Quick start

This reads one Secret Manager secret into a Kubernetes Secret, signing with
an access key pair. On Ncloud Kubernetes Service, `auth.podIdentity` and
`auth.serverRole` avoid storing a key; see [Authentication](#authentication).

1. In the NAVER Cloud Platform console, create a secret named `app-secret`
   in Secret Manager with the value `{"password": "s3cr3t"}`.
2. Save the following as `quickstart.yaml`, fill in an access key pair that
   may list and read secrets (the `NCP_VPC_SECRET_MANAGER_VIEWER` policy is
   enough; see the
   [required permissions](docs/provider/ncloud.md#required-permissions)),
   and apply it with `kubectl create namespace demo` and
   `kubectl apply -f quickstart.yaml`. The endpoint serves secrets protected
   by an isolated KMS key in KR; pick another from
   [Compatibility](#compatibility) if the secret is elsewhere.

   ```yaml
   apiVersion: v1
   kind: Secret
   metadata:
     name: ncloud-credentials
     namespace: demo
   stringData:
     access-key-id: <NCLOUD_ACCESS_KEY_ID>
     secret-key: <NCLOUD_SECRET_KEY>
   ---
   apiVersion: external-secrets.io/v1
   kind: SecretStore
   metadata:
     name: ncloud
     namespace: demo
   spec:
     provider:
       ncloud:
         endpoint: https://ocapi-kr.ncloud.com/secretmanager
         auth:
           secretRef:
             accessKeyIDSecretRef:
               name: ncloud-credentials
               key: access-key-id
             secretKeySecretRef:
               name: ncloud-credentials
               key: secret-key
   ---
   apiVersion: external-secrets.io/v1
   kind: ExternalSecret
   metadata:
     name: app-secret
     namespace: demo
   spec:
     refreshInterval: 1h
     secretStoreRef:
       kind: SecretStore
       name: ncloud
     target:
       name: app-secret
     data:
       - secretKey: password
         remoteRef:
           key: app-secret
           property: password
   ```

3. Check that the store is valid and the secret synced:

   ```bash
   kubectl -n demo get secretstore ncloud          # STATUS Valid, READY True
   kubectl -n demo get externalsecret app-secret   # STATUS SecretSynced, READY True
   kubectl -n demo get secret app-secret -o jsonpath='{.data.password}' | base64 -d
   ```

   A store that is not ready carries only fixed text in its condition and
   events; the controller log names the cause
   (`kubectl -n external-secrets logs deploy/external-secrets`), and the
   [provider documentation](docs/provider/ncloud.md#store-readiness)
   explains each cause.

## Authentication

| Method | Signs requests with | Stored in the cluster |
|---|---|---|
| `auth.secretRef` | a permanent access key pair from a Kubernetes Secret | the key |
| `auth.serverRole: {}` | the temporary key of the node's Server Role (the node pool's Node IAM Role on NKS), read from the instance metadata endpoint with a Metadata v2 token | nothing |
| `auth.podIdentity: {}` | the temporary key of the role associated with the controller pod's ServiceAccount through Pod Identity | nothing |
| any of them, plus `role:` | the temporary key of a switched role via the Secure Token Service | as above |

`serverRole` and `podIdentity` are accepted only in a `ClusterSecretStore`
and should be published with `conditions` that limit the namespaces allowed
to use the node's or the controller's role. `podIdentity` also needs the
controller pod to carry the label `nks.ncloud.com/pod-identity: "true"`,
which this chart does not set: add it through `podLabels` (see
[Pod Identity](docs/provider/ncloud.md#pod-identity-podidentity)). The
[provider documentation](docs/provider/ncloud.md) lists the permissions each
operation needs.

## Behavior to know before you rely on it

- A `remoteRef.key` must be a secret name that matches
  `^[A-Za-z][A-Za-z0-9_-]{2,14}$` or a 64-character lowercase hexadecimal
  secret ID.
  Any other key is an error that leaves the target Secret untouched; it is
  never reported as a missing secret.
- A value read of a secret whose deletion was requested (`REVOKE`) or that
  was destroyed reports it as absent, which is what `deletionPolicy` acts
  on; for a `REVOKE` secret, `metadataPolicy: Fetch` returns its metadata
  with that status. A paused (`DISABLE`) secret is an error, not absence,
  because its value still exists.
- `find` fails closed: a disabled secret that matches the selector, a read
  failure, or a listing that keeps changing across re-reads fails the whole
  `find` and keeps the last synced data. A secret deleted while `find` reads
  it is skipped.
- Secret Manager has no tags, so `find.tags` and pushing tags are rejected.
  A value is a JSON object of string leaves, 1 to 100 entries and at most
  10,000 bytes, enforced by the service.
- During the grace period after a delete, the secret keeps its name and the
  provider refuses to create a new secret with it; cancel the deletion and
  enable the secret, or wait for the destroy.
- `GET` requests retry transient failures up to three times within a
  45-second budget per request. Mutating requests are not retried, except
  for one re-send when a request signed with a temporary key is refused
  (a 401, or a 404 carrying the API Gateway's code `300`), which applies to
  every request.

The full list, with the service limits behind each rule, is in the
[provider documentation](docs/provider/ncloud.md).

## Versioning and upstream tracking

A release of this fork carries the version of the upstream release it is
based on: `v2.14.0` here is upstream v2.14.0 plus the `ncloud` provider and
the changes listed under [Changes from upstream](#changes-from-upstream).
The image and the chart of a release therefore have the same version as
upstream's and are not upstream's, so install this fork's chart by its
release URL, not by version from upstream's chart repository. When the fork
releases again on the same upstream base, for a fix in the `ncloud`
provider or a rebuild, it raises the patch number, and from then on the
number can be ahead of upstream's. It tags a release whose number is ahead
of its base's only while that base is still upstream's latest patch release
of that minor: once upstream has published a later one, the fork moves to
the latest one first, so a fork release never carries a number that
upstream has already used for a release other than its base. If upstream
later publishes that patch number itself, the two share a number and not
their contents, and a fork release based on it takes the patch number after
the fork's latest. A version number alone therefore does not say which
upstream release a fork release contains; the table does:

| Fork release | Upstream base |
|---|---|
| v2.14.0 | v2.14.0 |

The fork follows upstream minor releases and picks up upstream security
fixes by moving to the release that contains them. No schedule is promised
for either.

## Building from source

```bash
make build                      # every provider, as upstream
make build PROVIDER=ncloud      # only the ncloud and kubernetes providers
make test
make reviewable                 # regenerates CRDs, chart docs and snapshots
make helm.package.release RELEASE=v2.14.0 IMAGE_TAG=v2.14.0  # release chart
```

`helm.package.release` writes `bin/chart/external-secrets-<version>.tgz`.
It generates the CRD templates, pins the three image tags to `IMAGE_TAG`
(the published image tag, which for a release is the release tag itself),
sets the chart version and appVersion from `RELEASE`, and checks that the
archive renders every CRD, the `ncloud` fields and no other image.

The upstream [developer guide](docs/contributing/devguide.md) describes the
tooling the `Makefile` expects.
